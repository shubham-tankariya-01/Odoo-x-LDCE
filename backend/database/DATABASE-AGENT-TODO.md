# Database Agent Todo - GlobeTrotter (Neon PostgreSQL)

## Mission

Provision the Neon PostgreSQL database, implement the canonical GlobeTrotter schema, and deliver realistic seeded data so the backend and frontend can demonstrate the full trip-planning flow without external APIs.

**Canonical source of truth:** `E:\Coding\Hackthon_Projects\Odoo-x-LDCE\schema_readme\GlobeTrotter_Schema.md`

Use the wireframe term **Section** throughout the database and API-facing names; do not rename it to `stop` or `trip_stop`.

## Scope boundary

Build the **core eight-hour model first**:

`users -> trips -> sections -> section_activities -> activities`, plus `cities` and `expenses`.

`community_posts`, `post_comments`, and `post_likes` are optional. Only migrate them if the core schema, seed data, and verification checks are complete.

## 2. Implement the core migration

- [ ] Create a migration directory (for example `db/migrations/`) and add a first migration named `001_initial_schema.sql`.
- [ ] Copy the table definitions from the canonical schema, adapting only for the selected migration runner.
- [ ] Enable `pgcrypto` before using `gen_random_uuid()`:

  ```sql
  CREATE EXTENSION IF NOT EXISTS pgcrypto;
  ```

- [ ] Create the core tables in dependency order:

  1. `users`
  2. `cities`
  3. `activities`
  4. `trips`
  5. `sections`
  6. `section_activities`
  7. `expenses`

- [ ] Preserve the schema's declared foreign-key delete behavior:

  - deleting a user cascades to their trips;
  - deleting a trip cascades to its sections and expenses;
  - deleting a section cascades to its scheduled activities and sets `expenses.section_id` to `NULL`;
  - deleting a city cascades to its catalogue activities; do not delete a city that is already referenced by a section.

- [ ] Add all schema indexes plus:

  ```sql
  CREATE UNIQUE INDEX uq_sections_trip_order
    ON sections (trip_id, order_index);

  CREATE INDEX idx_section_activities_scheduled_date
    ON section_activities (scheduled_date);
  ```

- [ ] Add database checks where safe:

  ```sql
  ALTER TABLE trips
    ADD CONSTRAINT chk_trips_date_range
    CHECK (end_date IS NULL OR start_date IS NULL OR end_date >= start_date);

  ALTER TABLE sections
    ADD CONSTRAINT chk_sections_date_range
    CHECK (end_date IS NULL OR start_date IS NULL OR end_date >= start_date);

  ALTER TABLE sections
    ADD CONSTRAINT chk_sections_budget_nonnegative CHECK (budget >= 0);

  ALTER TABLE activities
    ADD CONSTRAINT chk_activities_cost_nonnegative CHECK (cost >= 0);

  ALTER TABLE expenses
    ADD CONSTRAINT chk_expenses_amount_positive CHECK (amount > 0);
  ```

- [ ] Keep cross-table validation in FastAPI/service logic: section dates inside trip dates, scheduled activity dates inside section dates, and section expense belonging to the same trip. PostgreSQL `CHECK` constraints cannot enforce these joins alone.

## 3. Seed catalogue and mock data

- [ ] Add `db/seeds/seed.sql` (or an equivalent reproducible seed command).
- [ ] Make the seed idempotent: rerunning it must not duplicate rows. Prefer deterministic UUIDs or `INSERT ... ON CONFLICT` for catalogue data.
- [ ] Seed **15-20 cities** across several regions, each with image URL, cost index, and popularity score.
- [ ] Seed **at least 5 activities per city** (75+ total) covering categories such as sightseeing, food, adventure, culture, nature, nightlife, and relaxation.
- [ ] Include a mix of free and paid activities, varied durations, and plausible costs.
- [ ] Seed two users with hashed passwords generated by the backend's actual password-hashing function. Do not use plaintext passwords in the database.
- [ ] Seed at least three trips for the primary demo user:

  - **Upcoming:** a 7-day, two-city trip with sections, activities, and expenses.
  - **Ongoing:** a short active trip for the trip-list status view.
  - **Completed:** a past trip for previous-trip cards.

- [ ] Ensure the upcoming demo trip has:

  - two or three ordered sections;
  - activities scheduled on multiple dates;
  - transport, stay, meal, and activity expenses;
  - at least one overridden activity cost;
  - totals that visibly differ by section for the budget screen.

- [ ] If optional community tables are implemented, seed only 3-5 posts with one comment/like each; do not spend core-demo time on social data.

## 4. Verify before handoff

- [ ] Run migrations against the Neon development database from a clean state.
- [ ] Run the seed command twice and confirm row counts stay stable.
- [ ] Verify foreign keys and indexes exist using `\d+` in `psql` or an information-schema query.
- [ ] Run this budget query successfully for the seeded upcoming trip (substitute the target trip id):

  ```sql
  SELECT
    COALESCE(SUM(COALESCE(sa.cost_override, a.cost)), 0)
      + COALESCE((SELECT SUM(e.amount) FROM expenses e WHERE e.trip_id = :trip_id), 0)
      AS estimated_total
  FROM section_activities sa
  JOIN sections s ON s.id = sa.section_id
  JOIN activities a ON a.id = sa.activity_id
  WHERE s.trip_id = :trip_id;
  ```

- [ ] Verify a nested itinerary query returns `trip -> sections -> section_activities` in `order_index`, then `scheduled_date`, then `scheduled_time` order.
- [ ] Record the demo credentials and demo trip name privately in the team handoff; never commit credentials.

## Definition of done

The database agent is done when a fresh developer can set `DATABASE_URL`, run migration + seed commands, sign in with a demo account, and see a multi-city itinerary with accurate budget data in the app.
